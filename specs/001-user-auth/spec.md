# Feature Specification: 使用者驗證與儀表板系統

**Feature Branch**: `001-user-auth`  
**Created**: 2025-12-05  
**Status**: Draft  
**Input**: User description: "建立一個應用系統，使用者能註冊、登入及登出系統，成功登入後能看見簡單的 dashboard"

## Clarifications

### Session 2025-12-23

- Q: 註冊成功後的導向/狀態是什麼？ → A: 註冊成功後自動登入並導向儀表板
- Q: 是否需要「記住我」？ → A: 需要；勾選後關閉瀏覽器仍保持登入（持久 cookie）
- Q: 是否需要 RBAC（多角色權限控制）？ → A: 需要；僅 admin 與 user 兩角色
- Q: admin 與 user 的權限差異是什麼？ → A: admin 可管理使用者（建立/停用/重設密碼）
- Q: 第一個 admin 要怎麼產生？ → A: 由部署者手動建立（資料種子/資料檔/資料庫預置）

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 使用者註冊 (Priority: P1)

新使用者透過提供基本資訊（電子郵件與密碼）建立帳號，完成註冊後可使用該帳號登入系統。

**Why this priority**: 這是系統的基礎功能，沒有註冊就無法建立使用者帳號，是所有其他功能的前提。

**Independent Test**: 可以透過訪問註冊頁面，填寫有效的電子郵件和密碼，提交後驗證帳號是否成功建立，且會自動登入並導向儀表板；不依賴其他使用者故事即可測試。

**Acceptance Scenarios**:

1. **Given** 使用者在註冊頁面，**When** 輸入有效的電子郵件（如 user@example.com）和符合規則的密碼（至少 8 個字元），**Then** 系統建立新帳號、建立會話並導向儀表板，且以 toast 顯示註冊成功訊息
2. **Given** 使用者在註冊頁面，**When** 輸入已存在的電子郵件，**Then** 系統以 toast 顯示「此電子郵件已被註冊」錯誤訊息
3. **Given** 使用者在註冊頁面，**When** 輸入無效的電子郵件格式（如 invalid-email），**Then** 系統以 toast 顯示「請輸入有效的電子郵件地址」錯誤訊息
4. **Given** 使用者在註冊頁面，**When** 輸入過短的密碼（少於 8 個字元），**Then** 系統以 toast 顯示「密碼必須至少 8 個字元」錯誤訊息

---

### User Story 2 - 使用者登入 (Priority: P1)

已註冊的使用者透過電子郵件和密碼登入系統，成功登入後進入儀表板頁面。

**Why this priority**: 登入是使用者存取系統的入口，與註冊同等重要，是 MVP 的核心功能。

**Independent Test**: 可以使用預先建立的測試帳號，在登入頁面輸入正確的帳號密碼，驗證是否成功登入並導向儀表板，不需要依賴註冊流程。

**Acceptance Scenarios**:

1. **Given** 已註冊使用者在登入頁面，**When** 輸入正確的電子郵件和密碼，**Then** 系統驗證身份並導向儀表板頁面
2. **Given** 使用者在登入頁面，**When** 輸入錯誤的密碼，**Then** 系統以 toast 顯示「電子郵件或密碼錯誤」訊息並保持在登入頁面
3. **Given** 使用者在登入頁面，**When** 輸入不存在的電子郵件，**Then** 系統以 toast 顯示「電子郵件或密碼錯誤」訊息
4. **Given** 使用者多次輸入錯誤密碼（超過 5 次），**When** 再次嘗試登入，**Then** 系統暫時鎖定該帳號並以 toast 顯示「帳號已被暫時鎖定，請稍後再試」訊息
5. **Given** 使用者在登入頁面且已勾選「記住我」，**When** 成功登入後關閉並重新開啟瀏覽器再訪問儀表板 URL，**Then** 系統仍視為已登入並顯示儀表板
6. **Given** 使用者在登入頁面且未勾選「記住我」，**When** 成功登入後關閉並重新開啟瀏覽器再訪問儀表板 URL，**Then** 系統要求重新登入並以 toast 顯示「請先登入」系統訊息

---

### User Story 3 - 使用者登出 (Priority: P2)

已登入的使用者可以安全地登出系統，登出後回到登入頁面，且無法存取需要驗證的頁面。

**Why this priority**: 登出是安全性的重要環節，但相對於註冊和登入是次要功能，可以在基本登入功能完成後再實作。

**Independent Test**: 使用已登入的使用者帳號，點擊登出按鈕，驗證使用者會話是否被清除，且被導向登入頁面。嘗試直接訪問儀表板 URL，應被導向登入頁面。

**Acceptance Scenarios**:

1. **Given** 使用者已登入並在儀表板頁面，**When** 點擊登出按鈕，**Then** 系統清除使用者會話並導向登入頁面，且以 toast 顯示登出成功訊息
2. **Given** 使用者已登出，**When** 嘗試直接訪問儀表板 URL，**Then** 系統自動導向登入頁面並以 toast 顯示「請先登入」系統訊息
3. **Given** 使用者已登出，**When** 點擊瀏覽器的「上一頁」按鈕，**Then** 系統仍然要求重新登入，不顯示之前的儀表板內容

---

### User Story 4 - 儀表板檢視 (Priority: P2)

已登入的使用者可以看到簡單的儀表板，顯示歡迎訊息和基本的使用者資訊（如電子郵件）。

**Why this priority**: 儀表板是登入後的主要頁面，提供使用者視覺回饋，但內容簡單，可以在登入功能完成後快速實作。

**Independent Test**: 使用已登入的測試帳號，訪問儀表板頁面，驗證是否正確顯示使用者資訊和歡迎訊息，不需要依賴其他功能。

**Acceptance Scenarios**:

1. **Given** 使用者已成功登入，**When** 進入儀表板頁面，**Then** 系統顯示「歡迎，[使用者電子郵件]」訊息
2. **Given** 使用者在儀表板頁面，**When** 檢視頁面內容，**Then** 系統顯示使用者的電子郵件和註冊日期
3. **Given** 未登入的使用者，**When** 直接訪問儀表板 URL，**Then** 系統導向登入頁面並以 toast 顯示系統訊息（例如：請先登入）

---

### User Story 5 - 管理者使用者管理 (Priority: P3)

admin 可以管理系統使用者：建立使用者、停用/啟用使用者、協助重設使用者密碼。

**Why this priority**: 這是管理功能，對 MVP（註冊/登入/儀表板/登出）不是阻塞，但需要在系統進入實際運作時提供基本管理能力。

**Independent Test**: 以 admin 身份登入後，執行建立使用者、停用使用者、重設密碼等操作，驗證被管理使用者的登入/存取行為符合預期。

**Acceptance Scenarios**:

1. **Given** admin 已登入，**When** 建立一個新使用者（email + 初始密碼），**Then** 系統建立該使用者帳號並以 toast 顯示成功訊息
2. **Given** admin 已登入且系統中存在一個 user，**When** admin 停用該 user，**Then** 該 user 之後嘗試登入時系統拒絕並以 toast 顯示「帳號已停用」系統訊息
3. **Given** admin 已登入且系統中存在一個 user，**When** admin 重設該 user 密碼，**Then** 該 user 必須用新密碼才能登入，且以 toast 顯示密碼已重設的成功訊息
4. **Given** user（非 admin）已登入，**When** 嘗試執行任何使用者管理操作，**Then** 系統拒絕該操作並以 toast 顯示「權限不足」錯誤訊息

### Edge Cases

- **重複提交註冊表單**：使用者快速點擊多次註冊按鈕時，系統應避免建立重複帳號
- **會話過期**：使用者登入後長時間未操作（超過 30 分鐘），再次操作時應被導向登入頁面
- **瀏覽器關閉後**：使用者關閉瀏覽器後重新開啟，若未勾選「記住我」，應需要重新登入；若已勾選，則應保持登入狀態
- **特殊字元密碼**：密碼包含特殊字元（如 @#$%）時，系統應正確處理而不產生錯誤
- **網路中斷**：在註冊或登入過程中網路中斷，系統應顯示友善的錯誤訊息而非崩潰
- **同時多處登入**：使用者在不同裝置或瀏覽器同時登入時，系統應允許多個活躍會話（或根據需求限制單一會話）

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 系統必須提供使用者註冊功能，接受電子郵件和密碼作為註冊資訊
- **FR-002**: 系統必須驗證電子郵件格式的有效性（符合標準電子郵件格式）
- **FR-003**: 系統必須要求密碼至少 8 個字元長度
- **FR-004**: 系統必須確保每個電子郵件地址只能註冊一次
- **FR-005**: 系統必須將密碼以加密方式儲存（使用 bcrypt 或 argon2 等強加密算法）
- **FR-006**: 系統必須提供使用者登入功能，接受電子郵件和密碼進行身份驗證
- **FR-007**: 系統必須在登入失敗時顯示通用錯誤訊息（「電子郵件或密碼錯誤」），避免洩露帳號存在資訊
- **FR-008**: 系統必須在連續 5 次登入失敗後暫時鎖定帳號 15 分鐘，防止暴力破解
- **FR-009**: 系統必須在使用者成功登入後建立安全的會話（Session）
- **FR-010**: 系統必須提供登出功能，清除使用者會話並導向登入頁面
- **FR-011**: 系統必須在會話過期（30 分鐘無活動）後自動登出使用者
- **FR-012**: 系統必須顯示儀表板頁面給已登入的使用者
- **FR-013**: 系統必須在儀表板上顯示使用者的電子郵件和註冊日期
- **FR-014**: 系統必須阻擋未登入使用者訪問儀表板頁面，將其導向登入頁面
- **FR-015**: 系統必須記錄所有身份驗證事件（註冊、登入成功、登入失敗、登出）到安全日誌
- **FR-016**: 系統必須在使用者註冊成功後自動登入並導向儀表板
- **FR-017**: 系統必須在登入頁面提供「記住我」選項；勾選時使用持久 cookie 保持登入（關閉瀏覽器後仍有效），未勾選時使用 session cookie（關閉瀏覽器後失效）
- **FR-018**: 系統必須支援基於角色的權限控制（RBAC），角色僅包含 `admin` 與 `user`
- **FR-019**: 系統必須在註冊時將新使用者的預設角色設為 `user`
- **FR-020**: 系統必須提供 admin 的使用者管理能力：建立使用者、停用/啟用使用者、重設使用者密碼
- **FR-021**: 系統必須拒絕非 admin 執行使用者管理操作，並回傳/顯示「權限不足」
- **FR-022**: 系統必須支援以手動方式預先建立第一個 `admin` 帳號（例如以資料種子/資料檔/資料庫預置）；該帳號必須能成功登入並執行使用者管理操作

### Key Entities

- **使用者（User）**: 代表系統的使用者帳號，包含唯一識別碼、電子郵件（唯一）、加密後的密碼、註冊日期、最後登入時間、帳號狀態（啟用/停用/鎖定）、角色（`admin`/`user`）
- **會話（Session）**: 代表使用者的登入狀態，包含會話識別碼、關聯的使用者、建立時間、最後活動時間、過期時間
- **安全日誌（Security Log）**: 記錄安全相關事件，包含事件類型（註冊/登入/登出）、使用者識別、時間戳記、IP 地址、操作結果（成功/失敗）

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 使用者可以在 2 分鐘內完成註冊流程（從開啟註冊頁面到看到成功訊息）
- **SC-002**: 使用者可以在 30 秒內完成登入流程（從開啟登入頁面到看到儀表板）
- **SC-003**: 系統在 1 秒內回應登入請求（包含密碼驗證時間）
- **SC-004**: 95%的使用者首次嘗試即可成功完成註冊（表單驗證清楚且易懂）
- **SC-005**: 系統支援至少 100 個同時登入的使用者而不影響效能
- **SC-006**: 所有身份驗證相關的安全事件都被完整記錄到日誌中
- **SC-007**: 密碼儲存符合業界安全標準（使用強加密算法，不可逆向）
- **SC-008**: 登出後的使用者無法透過任何方式存取需要驗證的頁面
